# 0033 — Custom components: raw RC JSON bodies, versioned by RC release

- Status: Accepted
- Date: 2026-11-26
- Amends: [0015](0015-screen-model-is-the-product.md) (screens stay the semantic model; a custom
  component's *body* is the one place raw Remote Compose JSON is allowed) and the direction in
  T-018 ("avoid exposing raw draw ops in the model"), which still holds for screens.

## Context

Owner, 2026-11-26: designs like a branded home screen (vector icons in brand colors, gradient
cards, shapes) need **any shape and custom components** beyond the built-in ones. These components
should be made in the panel, also with an LLM, saved under a name and reused on many screens.

Options weighed in the conversation:

1. **Our own declarative shape format** (shapes in a `viewBox`, params, children). Stable, and we
   control it. But it is a second drawing language to design, document and teach an LLM, and it
   always lags behind RC.
2. **Kotlin RC DSL generated by an LLM, compiled on the server.** This runs generated code on the
   server, and the `@RestrictTo` API breaks stored components on upgrades. Rejected.
3. **Replace the whole screen format with RC JSON.** This is too low level for the visual editor
   and the data wizard: a "button that opens screen X" becomes box + text + `hostAction`, and turning
   it back into a component tree is decompiling. RC JSON also has no data sources, bindings,
   `repeat`, image URLs or per-client API levels, and every alpha would migrate every stored screen.
   Rejected.
4. **Raw RC JSON (`RemoteComposeJsonParser`) only inside custom component definitions**; screens
   reference them by name. The owner chose this: LLMs work well with it, and versioning replaces
   forced compatibility.

Spike (2026-11-26, alpha23, branch `spike/rc-json-fragment`, facts in
[remote-compose.md → RC JSON](../remote-compose.md#rc-json-remotecomposejsonparser--spike-for-custom-components-verified-alpha23-2026-11-26)):
- A fragment parsed into **our** `RemoteComposeWriter` in the middle of an `RcScope` column renders
  correctly on the real player. Its `hostAction("navigate:parcels")` arrives as `Action.Navigate`.
- Public `parse()` only accepts whole documents. A single component needs the package-private
  `parseComponent`, which means a bridge class declared in package
  `androidx.compose.remote.creation.json`.
- `definePattern` (RC macros with parameters) works when parsed before `root {}`.
- RC JSON has no `image` component, and a JSON `canvas` silently drops `children`.

## Decision

- **Screens stay semantic** (ADR 0015). A new component type `custom`
  (`{ "type": "custom", "component": "<id>", "args": { … } }`) references a **component
  definition** by id.
- **A component definition** is data: `id`, `version`, `rcVersion` (the RC release it was validated
  against), `minApiLevel`, typed `params`, and `body` (RC JSON, one root component). It is stored
  next to screens: `components/<id>.json` in the data directory, and in `server-store` with
  drafts, publish and history like screens.
- **Rendering:** `render/` substitutes `args` (already bound to data) into `{{params.<name>}}`
  values of the body. It substitutes in the JSON tree, never by string concatenation. It then parses
  the body with `RemoteComposeJsonParser` into the same writer, at the component's place in the
  document. The bridge to `parseComponent` is the only code in the parser's package. It lives in
  `sdk-server/.../render/` (R1 still holds: RC API only there). `org.json` becomes a server
  dependency.
- **Safety:** the body must pass a whitelist (component types, canvas commands, modifiers),
  size/count limits, and `hostAction` names that `ActionCodec` decodes. No native `custom` views,
  runtime shaders, particles or sound until a task allows them. Images come only through our image
  pipeline (T-026). A `canvas` with `children` is an error, not a silent drop.
- **Versioning instead of compatibility:** an RC upgrade re-validates every stored definition (parse,
  render, PNG). A definition that fails is marked `broken`; screens render a fallback (nothing) in
  its place and `/debug` warns. Fixing it creates a new `version`; the LLM may propose the fix. A
  client below `minApiLevel` gets the fallback instead of a 426 for the whole screen.
- **Authoring:** a JSON editor with the same validation and a `preview-renderer` image. The AI chat
  that writes bodies is part of T-033. Validation errors carry the parser's `ContextPath` so an LLM
  can fix its own output.

## Consequences

- Any shape, gradient or icon RC can draw is available without a new built-in component.
- Two languages now exist: our model for screens and RC JSON for component bodies. The visual editor
  treats a custom component as a black box with a form for its params.
- The bridge depends on a package-private RC method and a private field (`mInFirstPass`, for
  patterns). Every RC upgrade can break it. The re-validation step and the upgrade playbook must run
  it.
- RC JSON modifier order is Compose order, unlike our unordered box model (ADR 0020). The authoring
  docs and the LLM prompt must say so.
- Bodies are not portable to another renderer (ADR 0015's "maybe another renderer" no longer
  covers custom components). This is acceptable: Android only (ADR 0022).

## How to verify it still holds

- `RcJsonComponentsTest` (sdk-server) and the `custom` golden in `compat-tests` (T-049) pass.
- After an RC upgrade, re-validating all definitions (T-049 step K4) reports none `broken`.
- `scripts/check-architecture.sh` R1: the bridge file is under `sdk-server/.../render/`.
